# 多语言 + AI 翻译（Phase 2）

## 〇、语言数受用户权限控制

用户能给自己的网站开**几种语言**，由其权限决定（不是无限开）。

- 具体怎么划分（按订阅套餐 / 按账号配额字段 / 其它）**暂不定**，先记下这个约束。
- 实现时：发布 / 启用语言前校验「已启用语言数 < 权限上限」，超了提示升级。

## 一、为什么放 Phase 2

MVP 先把单语言闭环做扎实，避免架构过早被多语言拖复杂。

## 二、多语言主线流程

操作主线（从建站到多语言）：

1. 用户选**后台界面语言**（如 en）
2. 建站选主题 → 系统拷该主题这门语言的整套 seed（见下一节）→ 这门语言成为该站**源语言**
3. 用户用**母语（源语言）填真实内容**
4. **逐篇 AI 翻译成目标语言**（如 ja）
5. 用户可微调翻译结果
6. 每种语言生成独立的静态目录（如 `/en/`、`/ja/`）
7. 自动按访客浏览器语言跳转，并提供切换器

「源语言」=用户建站时选的、用来填内容的语言，没有平台固定的默认语言。

## 二之一、主题提供多语言整套 seed

主题按语言分整套 seed，存于 `themes/<name>/i18n/<lang>/`（每语言一整套，含 `settings.yaml` + `pages/*.yaml` + `data/*.yaml`）。主题 `meta.yaml` 的 `languages` 字段声明本主题提供哪些语言的 seed（如 `languages: [en, zh, ja]`）。

建站时按用户选的语言拷对应那套：用户选 en 且主题 `meta.languages` 含 en，系统就把 `themes/<name>/i18n/en/` 整套拷到 `sites/<id>/`，于是站点的 `settings.yaml`、`pages/`、`data/` 就是源语言的初始内容；`settings.default_language` 记为 en。AI 翻译的目标语言产出落在 `sites/<id>/lang/<目标语言>/`。

## 三、翻译的核心难题

不是「能不能翻」，而是「持续维护」：

| 难题          | 严重程度 | 应对                              |
| ------------- | -------- | --------------------------------- |
| 翻译质量      | 中       | LLM 已够用，glossary 解决术语     |
| HTML 结构破坏 | 大       | 抠出文本节点单独翻                |
| 同步问题      | **最大** | hash 缓存识别变化                 |
| 品牌词乱翻    | 中       | 词汇表保护                        |
| 成本          | 小       | 缓存 + 便宜模型，单位成本低 |

## 四、三层翻译策略

```text
源文本（源语言）
    │
    ▼
Layer 1: 词汇表 (Glossary)
完全替换 / 不翻译的词
"小米" → "Xiaomi"，"门锁 Pro" → 不翻
    │
    ▼
Layer 2: 人工覆盖 (Override)
关键页（首页、关于）人工写好的英文
优先级最高
    │ 没有覆盖时
    ▼
Layer 3: AI 自动翻译
数据条目（产品、案例）走这个，hash 缓存
```

AI 翻译方向是**源语言 → 目标语言**（不固定中到英；源语言由用户建站时选定）。

为什么分层：

- 首页 / 关于这种**门面页**人工翻译（数量少，质量重要）
- 产品 / 案例这种**长尾内容**走 AI（数量多，质量要求适中）
- 公司名 / 品牌词全局保护（错一次就尴尬）

## 五、同步问题：hash 缓存

每段源语言文本算一个 hash，翻译表用 hash 做 key：

```text
products[1].name = "智能门锁 Pro"  →  hash = a3f2...
translations[en][a3f2...] = "Smart Lock Pro"

源文本改了:
products[1].name = "智能门锁 Pro 2 代"  →  hash = b7e1...
→ 找不到对应翻译 → 标记为"待翻译"
→ 老翻译保留为参考（"Smart Lock Pro"）
→ 显示给用户审核
```

效果：

- 源文本不变 → 译文一直在，不重复花钱翻译
- 源文本改了 → 系统知道哪条需要重译
- 老译文当参考，用户不用从零看

## 六、HTML 保护

不要把 HTML 整段送 LLM。用 BeautifulSoup 抠出文本节点：

```text
原文: <p>我们的<strong>智能门锁</strong>是行业领先的</p>

抠出: ["我们的", "智能门锁", "是行业领先的"]
       ↓ 翻译
       ["Our ", "smart lock", " is industry-leading"]
       ↓ 注回
结果: <p>Our <strong>smart lock</strong> is industry-leading</p>
```

英文边界空白处理需要小心，但是细节问题。

## 七、词汇表的存储

每个用户可以维护一份 `glossary.yaml`：

```yaml
do_not_translate:
  - 智能门锁 Pro
  - 我的公司
  - LOGO

force_translate:
  # key 为「源语言_to_目标语言」，方向随用户的源语言而定
  zh_to_en:
    "联系我们": "Contact Us"
    "了解更多": "Learn More"
    "关于": "About"
```

这个文件让 AI 帮用户预填，用户只需审核。

## 八、用户操作流程

```text
1. 用户用源语言（母语）填完所有内容
2. 设置 → 启用一门目标语言
3. 系统：
   - 扫描所有文本，算 hash，查缓存（无变化的不重译）
   - 套用 glossary
   - 用 LLM 把源语言翻译成目标语言（剩下未缓存的）
   - 显示 cost 预估（"将翻译 47 段，预计 ¥0.3"）
4. 用户确认 → 真正翻译
5. 翻译完成进入审核界面：
   - 源语言与目标语言并排显示
   - 可逐条修改
   - 改过的会被记到 override，下次不再 AI 翻译
6. 满意了 → 发布
```

## 九、技术细节

- 默认模型：gpt-4o-mini 或国产同级（性价比高）
- 支持用户自带 API key（可选）
- 翻译以「站点 + 语言 + hash」做唯一索引缓存
- 数据集独立翻译批次，避免一次任务超长
- Prompt 注入"已翻译过的术语清单"保证风格一致

## 十、发布流程

每种语言独立生成一份目录（`/zh/`、`/en/`），sitemap 包含所有语言的 URL，
HTML 头部加 `hreflang` 标签让搜索引擎理解。

字体子集化（[publish.md](site/publish.md)）按语言分别做 —— 各语言只装自己需要的字符集（如英文版不需要中文字体）。

## 十一、不做的事

| ❌ 不做                    | 为什么                         |
| -------------------------- | ------------------------------ |
| 自动检测访客语言并显示     | 用 302 重定向 + 用户切换器即可 |
| 翻译记忆库（TM）           | 小企业用不上                   |
| 术语表管理 UI（高级）      | 一份 YAML 够用                 |
| 实时翻译（访客访问时翻译） | 违背静态网站理念               |
| 强制翻译所有语言           | 用户自由勾选启用哪几种         |
