# 多语言 + AI 翻译（Phase 2）

> **i18n 是 internationalization 的缩写** —— 第一个字母 i，最后一个字母 n，中间省 18 个字母。意思就是「多语言支持」。
>
> 创始人自己的网站需要多语言（贸易类公司的常见需求），所以从原 Phase 4 提到 Phase 2。
> Phase 1 MVP 先验证单语言流程，避免架构过早被多语言拖复杂。

## 一、为什么是 Phase 2 而不是 MVP

- MVP 第一版先把单语言闭环做扎实
- 创始人 dogfooding 阶段自己上多语言 → 验证 + 打磨
- 验证完产品化，对外开放

分两步走：

| 阶段     | 内容                                            | 谁用       |
| -------- | ----------------------------------------------- | ---------- |
| Phase 2a | 词汇表 + AI 翻译 + hash 缓存（无 UI，文件配置） | 创始人自己 |
| Phase 2b | 加管理 UI、费用预估、多语言扩展                 | 所有店主   |

## 二、远期愿景

> "用户设计一次，多语言输出"

- 店主只在母语下填内容
- 一键 AI 翻译生成英 / 日 / 韩等版本
- 店主可微调翻译结果
- 每种语言生成独立的静态目录（`/zh/`、`/en/`）
- 自动按访客浏览器语言跳转，并提供切换器

## 三、翻译的核心难题

不是「能不能翻」，而是「持续维护」：

| 难题          | 严重程度 | 应对                              |
| ------------- | -------- | --------------------------------- |
| 翻译质量      | 中       | LLM 已够用，glossary 解决术语     |
| HTML 结构破坏 | 大       | 抠出文本节点单独翻                |
| 同步问题      | **最大** | hash 缓存识别变化                 |
| 品牌词乱翻    | 中       | 词汇表保护                        |
| 成本          | 小       | 缓存 + 便宜模型，单位成本低 |

## 四、三层翻译策略

```text
源文本（中文）
    │
    ▼
Layer 1: 词汇表 (Glossary)
完全替换 / 不翻译的词
"小米" → "Xiaomi"，"门锁 Pro" → 不翻
    │
    ▼
Layer 2: 人工覆盖 (Override)
关键页（首页、关于）人工写好的英文
优先级最高
    │ 没有覆盖时
    ▼
Layer 3: AI 自动翻译
数据条目（产品、案例）走这个，hash 缓存
```

为什么分层：

- 首页 / 关于这种**门面页**人工翻译（数量少，质量重要）
- 产品 / 案例这种**长尾内容**走 AI（数量多，质量要求适中）
- 公司名 / 品牌词全局保护（错一次就尴尬）

## 五、同步问题：hash 缓存

每段中文文本算一个 hash，翻译表用 hash 做 key：

```text
products[1].name = "智能门锁 Pro"  →  hash = a3f2...
translations[en][a3f2...] = "Smart Lock Pro"

中文改了:
products[1].name = "智能门锁 Pro 2 代"  →  hash = b7e1...
→ 找不到对应翻译 → 标记为"待翻译"
→ 老翻译保留为参考（"Smart Lock Pro"）
→ 显示给店主审核
```

效果：

- 中文不变 → 英文一直在，不重复花钱翻译
- 中文改了 → 系统知道哪条需要重译
- 老译文当参考，店主不用从零看

## 六、HTML 保护

不要把 HTML 整段送 LLM。用 BeautifulSoup 抠出文本节点：

```text
原文: <p>我们的<strong>智能门锁</strong>是行业领先的</p>

抠出: ["我们的", "智能门锁", "是行业领先的"]
       ↓ 翻译
       ["Our ", "smart lock", " is industry-leading"]
       ↓ 注回
结果: <p>Our <strong>smart lock</strong> is industry-leading</p>
```

英文边界空白处理需要小心，但是细节问题。

## 七、词汇表的存储

每个店主可以维护一份 `glossary.yaml`：

```yaml
do_not_translate:
  - 智能门锁 Pro
  - 我的公司
  - LOGO

force_translate:
  zh_to_en:
    "联系我们": "Contact Us"
    "了解更多": "Learn More"
    "关于": "About"
```

这个文件让 AI 帮店主预填，店主只需审核。

## 八、店主操作流程

```text
1. 店主在中文模式下填完所有内容
2. 设置 → 启用 English
3. 系统：
   - 扫描所有文本，算 hash，查缓存（无变化的不重译）
   - 套用 glossary
   - 用 LLM 翻译剩下的
   - 显示 cost 预估（"将翻译 47 段，预计 ¥0.3"）
4. 店主确认 → 真正翻译
5. 翻译完成进入审核界面：
   - 中英并排显示
   - 可逐条修改
   - 改过的会被记到 override，下次不再 AI 翻译
6. 满意了 → 发布
```

## 九、技术细节

- 默认模型：gpt-4o-mini 或国产同级（性价比高）
- 支持用户自带 API key（可选）
- 翻译以「站点 + 语言 + hash」做唯一索引缓存
- 数据集独立翻译批次，避免一次任务超长
- Prompt 注入"已翻译过的术语清单"保证风格一致

## 十、发布流程

每种语言独立生成一份目录（`/zh/`、`/en/`），sitemap 包含所有语言的 URL，
HTML 头部加 `hreflang` 标签让搜索引擎理解。

字体子集化（[publish.md](publish.md)）按语言分别做 —— 英文不需要中文字体。

## 十一、不做的事

| ❌ 不做                    | 为什么                         |
| -------------------------- | ------------------------------ |
| 自动检测访客语言并显示     | 用 302 重定向 + 用户切换器即可 |
| 翻译记忆库（TM）           | 小企业用不上                   |
| 术语表管理 UI（高级）      | 一份 YAML 够用                 |
| 实时翻译（访客访问时翻译） | 违背静态网站理念               |
| 强制翻译所有语言           | 店主自由勾选启用哪几种         |
