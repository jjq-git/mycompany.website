# 模板与块系统

## 一、模板是什么

**模板** = 一个文件夹，里面有：

- 整站的视觉风格（颜色、字体、间距）—— CSS 文件
- 各页面的结构（页眉、页脚、首页 Banner、产品页等）—— Jinja2 模板
- 每个数据块对应的字段定义（"产品"有哪些字段）—— YAML schema
- 一份假数据，让店主第一次进来就能看到完整效果 —— YAML seed_data

由开发者 + AI 制作，**git 管理**。
店主选一个模板，整站立即可用，然后只需要把假数据替换成真数据。

模板按行业分类：

| 行业   | 模板内容                          |
| ------ | --------------------------------- |
| 制造业 | 产品列表 + 案例 + 资质证书 + 联系 |
| 餐饮   | 菜单 + 门店地址 + 预订表单        |
| 服务业 | 服务项目 + 团队介绍 + 在线预约    |
| 贸易   | 产品目录 + 公司实力 + 询价表单    |
| 工作室 | 作品集 + 关于 + 联系              |

**MVP 阶段只做 3 套**（覆盖最大市场），之后逐步增加。

## 二、模板的文件结构

```text
site_templates/manufacturing-standard/
├── meta.yaml                  # 模板元信息（名称、行业、封面图、版本）
├── pages/                     # 页面 Jinja2 模板
│   ├── home.html
│   ├── products.html          # 产品列表（数据块）
│   ├── product_detail.html    # 产品详情（数据块）
│   ├── about.html
│   └── contact.html
├── blocks/                    # 共享块
│   ├── header.html
│   ├── footer.html
│   └── breadcrumb.html
├── styles/
│   └── theme.css              # 整套模板的样式（含 CSS 变量定义主色）
├── schema.yaml                # 数据集字段定义
└── seed_data/                 # 假数据
    ├── products.yaml
    ├── cases.yaml
    └── settings.yaml
```

新增模板 = 复制一个文件夹改改。git 全程可见。

## 三、模板的灵活性（参数化能力）

模板不是「固定不变」。模板 = **渲染规则 + 数据槽位**。
一个好模板能覆盖大量变体，靠三种参数化：

### 数据列表（任意数量）

| 元素                       | 由数据决定     |
| -------------------------- | -------------- |
| 菜单项                     | 1 ~ N 个       |
| 产品 / 案例 / 博客         | 0 ~ N 条       |
| 首页轮播图                 | 1 ~ N 张       |
| 联系方式（电话/微信/邮箱） | 想列几个填几个 |
| 页脚链接                   | 自由组合       |

例：菜单的布局、悬停效果、移动端折叠都在模板里写死；
菜单项是数据，店主想 4 个就填 4 个，5 个就填 5 个 —— **模板不变**。

### 开关式选项（要不要显示）

| 开关         | 说明                     |
| ------------ | ------------------------ |
| 顶栏显示电话 | ✓ / ✗                    |
| 客户评价区   | ✓ / ✗                    |
| 备案号       | ✓ / ✗                    |
| 在线客服按钮 | ✓ / ✗                    |
| 语言切换器   | 自动（开了多语言才出现） |

### 主题变量（视觉调整）

| 变量     | 可选值                             |
| -------- | ---------------------------------- |
| 主色     | 任意颜色                           |
| 字体     | 思源黑体 / 阿里普惠 / OPPO Sans... |
| 圆角     | 直角 / 圆润 / 柔和                 |
| 间距密度 | 紧凑 / 标准 / 宽松                 |

### 这些参数都存在哪

不在模板里，在店主的 `SiteSettings` 中（详见 [architecture.md](architecture.md)）。
模板渲染时读取，没有就用模板的 default。

### 模板做不到什么

承认有些差异确实需要换模板：

| 场景               | 模板能盖吗  | 解法                              |
| ------------------ | ----------- | --------------------------------- |
| 菜单 4 个 vs 5 个  | ✅ 数据列表 | 店主自己加                        |
| 中文 / 英文 / 双语 | ✅ 配置     | 设置开关                          |
| 主色红色 vs 蓝色   | ✅ 主题变量 | 设置选色                          |
| 制造业风 vs 餐饮风 | ❌          | 选不同模板                        |
| 单页式 vs 多页式   | ❌          | 选不同模板                        |
| 产品 3 列 vs 5 列  | 看模板设计  | 模板可提供"卡片式 / 列表式"等变体 |

模板设计的真本事是**判断哪些维度需要参数化、哪些可以写死**。
参数化太多 → 模板代码复杂、店主选项焦虑
参数化太少 → 客户说"差一点就完美"但用不了

Shopify 12 套模板能撑起千亿生意，靠的是每套都有 50+ 参数化选项。
看起来是 12 个模板，实际是 12 × 上千种组合。

## 四、模板的制作工作流

```text
设计师在 Figma 画原型
        ↓
AI（Claude 等）把原型转成 HTML + CSS
        ↓
开发者微调 + 加 Jinja2 占位符 + 写 schema.yaml
        ↓
本地 flask run 预览
        ↓
git commit + push
        ↓
平台加载新模板，店主可选
```

为什么不用可视化编辑器：

- 模板少（3-5 套），打磨稀少而精
- 2026 年 AI 写 HTML / CSS 已经很好用
- 代码可以 git diff、code review、AI 直接修改
- 不必为"可视化编辑"承担一整个子系统的复杂度

## 五、块的三种类型

每个模板预设若干块。**店主不能自己造块，只能用模板提供的块。**

### 共享块

整站共用，改一处全站生效。

| 例子                      | 店主能改什么             |
| ------------------------- | ------------------------ |
| 页眉（Logo + 菜单）       | Logo 图片、公司名        |
| 页脚（联系方式 + 备案号） | 电话、邮箱、地址、备案号 |
| 面包屑                    | 自动生成，店主不用改     |

### 内容块

每页自己的内容，店主填字段。

| 例子        | 店主填的字段                     |
| ----------- | -------------------------------- |
| 首页 Banner | 主标题、副标题、按钮文字、背景图 |
| 关于我们    | 公司简介（富文本）+ 几张图       |
| 联系我们    | 地址、电话、邮箱、地图坐标       |

### 数据块

由数据集循环生成。**店主只录数据，不碰设计**。

| 例子     | 数据集   | 自动生成                                                                 |
| -------- | -------- | ------------------------------------------------------------------------ |
| 产品列表 | 产品集合 | `products/index.html` + `products/data.json`（JS 处理筛选/分页）         |
| 产品详情 | 同上     | `products/product_<id>.html` 每个产品一个 HTML（SEO 友好，预生成）       |
| 案例集   | 案例集合 | 同上模式：`cases/index.html` + `cases/data.json` + 每个 `case_<id>.html` |
| 博客     | 文章集合 | 同上模式                                                                 |

**列表 + 详情的混合策略**：详情页预生成（SEO 关键），列表页一份 HTML + 一份 JSON 由 JS 驱动筛选/分页/排序（详见 [publish.md](publish.md)）。
源数据只有一份 `data/<name>.yaml`，生成器按需抽字段。

## 六、智能块（依赖渲染上下文）

有几个块在渲染时需要知道"我现在在哪个页面"：

- **菜单**：高亮当前页所在的菜单项
- **面包屑**：根据当前页生成层级
- **语言切换器**：知道当前语言（Phase 2）

实现思路：渲染器维护一个「上下文」对象，渲染这些块时把当前页面信息传进去。

## 七、数据集的概念

每种数据块对应一个数据集。每个数据集有固定的字段定义（由模板的 `schema.yaml` 决定）。

### 例：制造业模板的「产品」数据集字段

| 字段     | 类型     | 必填 |
| -------- | -------- | ---- |
| 产品名称 | 文本     | ✓    |
| 主图     | 图片     | ✓    |
| 简介     | 短文本   | ✓    |
| 价格     | 数字     |      |
| 详细描述 | 富文本   |      |
| 规格参数 | 键值对   |      |
| 多图     | 图片列表 |      |

店主在后台看到的就是这些字段的表单 —— **没有编程概念，只是填字段**。

## 八、模板与店主网站的关系

```text
模板（git 管理，所有店主共享）          店主网站（sites/<id>/ 文件夹）
─────────────────────                 ──────────────────────
HTML / Jinja2 模板    ◀──────  不能改
CSS                  ◀──────  不能改（保证视觉一致）
schema.yaml          ◀──────  不能改

                     ──────▶  字段值（店主填的）
                     ──────▶  上传的图片
                     ──────▶  数据条目（产品、案例）
                     ──────▶  全局设置（Logo、主色、电话）
```

模板升级（开发者改了模板代码 + git push）→ 所有用这个模板的店主网站**自动获益**，
因为店主只填了数据，不持有模板代码。

## 九、版本与升级

### 字段位置

- 模板自身：`meta.yaml.version`（语义版本号）
- 店主站点：`Site.template_version`（建站时记录当时模板的版本）
- 渲染时：builder 会比对两者，不一致**只打警告**（`current_app.logger.warning`），不阻塞

### 升级策略

| 改动类型 | 怎么处理 |
| --- | --- |
| 修 bug / 加可选字段 | 直接改模板 → 所有站点自动获益（`meta.yaml.version` 也升一下，便于对账） |
| 破坏性改动 | **复制模板目录**：`tech-product/` → `tech-product@0.1.0/`，新版继续占用 `tech-product/`。原本指向 `tech-product` 的老站，把 `Site.template_name` 改成 `tech-product@0.1.0` 即可冻结 |

### 现阶段（MVP）

不预先做版本目录。等真出现破坏性改动时再分目录，那时才知道要冻结哪些老站。
版本号字段先存着，是为将来留信息，不是现在就用。

## 十、典型的"20 个产品"场景

这是产品的核心使用场景，理解它就理解了产品的灵魂：

```text
店主想加 20 个产品。

旧的设计（错的）：每个产品都进编辑器拖拽设计页面 → 痛苦
我们的设计（对的）：店主进「产品管理」表格 → 点 20 次「添加产品」→ 填表
                  → 系统自动生成 20 个产品详情页 + 列表页 + 分页

店主全程不碰任何"设计"工作。
开发者早就把"产品页长什么样"的模板写好了。
```
