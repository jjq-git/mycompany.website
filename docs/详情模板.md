# 详情模板

## 结论

结合当前项目实现，详情模板不应该从零设计成一套独立页面编辑器。

当前项目已经有这些基础：

- 列表菜单 `type=list` 会对应一个数据集，例如 `products`
- 数据集存放在 `sites/<site_id>/data/<dataset>.yaml`
- 列表页配置存放在 `sites/<site_id>/pages/<dataset>.yaml`
- 列表页通过页面模块渲染，常用模块是 `data_grid`
- 详情页由 `menu.collect_render_tasks()` 自动生成，路径是 `/<菜单路径>/<slug>/`
- 详情页模板优先使用 `product_detail.html` / `case_detail.html` / `<dataset>_detail.html`
- 找不到专用详情模板时，回退到 `_generic_detail.html`
- `_generic_detail.html` 当前已经支持读取 `item.modules`
- 如果数据项没有 `modules`，详情页会自动渲染一个默认 `item_data` 模块
- 数据集编辑面板 `panel_data_list.html` 当前已经可以给单条数据编辑模块，并支持详情预览

所以，详情模板的正确演进方向是：

> 把当前“每条数据项保存 modules”的能力，提升为“列表级默认详情模板 + 单条数据项受控覆盖”。

这样最贴合现有代码，也最符合“用户填表，不写代码”的产品定位。

更准确地说：

> 详情模板不是“预设一篇详情内容”，而是“定义这类详情页需要哪些组件、每个组件读取哪些字段、组件如何在前台渲染”。

例如产品“LED 灯条”的详情模板，不应该固定塞进一大段默认内容，而应该允许用户按需要添加组件：

- 需要主图，就添加主图 / 媒体组件
- 需要细节图，就添加图集 / 轮播组件
- 需要参数，就添加规格表格组件
- 需要说明文字，就添加文本 / 富文本组件
- 需要下载资料，就添加链接 / 按钮组件
- 需要相关产品，就添加相关数据组件
- 需要 SEO、分类、标签规则，就在模板基础设置或规则组件中配置

创建详情模板时，系统可以生成“空模板骨架”或“最小可用模板”，但不应该把所有可能字段都默认塞进去。模板编辑的核心动作应该是“添加组件、配置组件、绑定字段、预览渲染效果”。

## 目标

列表菜单的数据项通常需要详情页，例如产品详情、案例详情、新闻详情。

详情模板用于定义这些详情页的渲染规则：

- 显示哪些模块
- 模块怎么排列
- 每个模块读取数据项里的哪些字段
- 字段如何展示
- 哪些内容可以自动生成
- 哪些样式允许配置
- 空字段如何处理

它的核心目标是：

- 用户只填数据，不写 HTML / CSS / JS
- 详情页可以复用统一结构
- 同一个列表可以有多个详情页呈现方式
- 同一个列表的数据项默认共用一套受控模板资源
- 特殊数据项可以通过高级入口做受控覆盖
- 发布结果仍然是静态 HTML

详情模板不是自由页面编辑器，也不是让用户改代码的模板系统。它应该被限制在：

```text
系统已有模块
字段绑定
显示规则
受控样式配置
自动生成规则
```

## 当前项目现状

### 列表页

当前列表菜单来自 `settings.yaml`：

```yaml
menu:
  - label: 产品中心
    type: list
    target: products
```

列表页配置来自：

```text
sites/<site_id>/pages/products.yaml
```

列表数据来自：

```text
sites/<site_id>/data/products.yaml
```

列表页通常使用 `data_grid` 这类模块读取数据集字段：

- `title` / `name`
- `cover` / `image` / `photo` / `logo`
- `summary` / `excerpt` / `description`
- `category`
- `tags`
- `price`
- `date`
- `slug`

这些字段应该保存在数据项中，而不是只存在列表页模块配置里。

### 详情页

当前详情页由 `app/core/menu.py` 自动推导：

```text
products -> product_detail.html
cases    -> case_detail.html
features -> feature_detail.html
其他     -> <dataset>_detail.html 或 _generic_detail.html
```

详情页输出路径：

```text
/<菜单路径>/<slug>/index.html
```

例如：

```text
/products/led-strip/index.html
```

当前 `_generic_detail.html` 的逻辑是：

```text
如果 item.modules 存在：
  按 item.modules 渲染详情页
否则：
  渲染默认 item_data 模块
```

这说明项目已经有“单条数据项详情模块”的能力。详情模板应该复用这条路径，而不是另起一套渲染系统。

## 推荐数据结构

详情模板建议存放在列表页配置里，也就是：

```text
sites/<site_id>/pages/<dataset>.yaml
```

原因：

- 列表页和详情模板天然归属于同一个列表菜单
- 当前项目已有 `pages/<dataset>.yaml` 作为列表页配置
- 不需要引入新的存储入口
- 构建时 `page_key` 已经能找到对应页面配置

推荐结构：

```yaml
modules:
  - type: data_grid
    variant: default
    data:
      dataset: products
      show_filters: "true"

detail_templates:
  - id: default
    name: 默认产品详情
    is_default: true
    modules:
      - type: item_data
        variant: default
        data:
          detail_images_max: 6
          show_arrows: "true"
          auto_scroll: "false"
    seo:
      title: "{title} - {site_name}"
      description: "{summary}"
      image: "cover"
    required_fields:
      - title
      - slug
      - cover
      - summary
```

数据项保存具体内容：

```yaml
- id: 1
  title: LED 灯条
  slug: led-strip
  cover: /assets/uploads/led-strip-cover.webp
  summary: 柔性低压灯带，适合展柜、家装和商业照明
  category: LED 照明
  tags:
    - LED
    - 灯条
  template_id: default
  detail_images:
    - url: /assets/uploads/led-strip-detail-1.webp
    - url: /assets/uploads/led-strip-detail-2.webp
  specs:
    - name: 功率
      value: 12W/m
    - name: 电压
      value: DC 24V
```

特殊数据项可以保留 `modules`，但它应该被定义为“高级覆盖”：

```yaml
- id: 2
  title: 重点产品
  slug: featured-product
  template_id: default
  modules:
    - type: item_data
      variant: default
      data:
        show_arrows: "true"
    - type: contact_info
      variant: list
      data:
        title: 获取报价
```

## 渲染优先级

详情页渲染时建议使用这个优先级：

```text
1. item.modules
   单条数据项的高级覆盖。当前项目已支持。

2. item.template_id 对应的 detail_templates[].modules
   数据项选择的详情模板。

3. 当前列表页的默认详情模板
   detail_templates 中 is_default=true 的模板。

4. 系统默认 item_data
   兜底，保持当前行为。
```

用伪代码表示：

```python
modules = (
    item.get("modules")
    or find_template(page.detail_templates, item.get("template_id")).modules
    or find_default_template(page.detail_templates).modules
    or [{"type": "item_data", "variant": "default", "data": {}}]
)
```

这个优先级有两个好处：

- 完全兼容当前 `item.modules` 实现
- 后续可以逐步把重复的 `item.modules` 收敛成列表级模板

## 模板中管理什么

详情模板应该管理五类配置：

```text
详情模板
  内容结构
  字段绑定
  显示规则
  样式配置
  自动生成规则
```

其中“内容结构”是第一优先级。先决定需要哪些组件，再决定每个组件需要哪些字段和规则。不要反过来先做一个包罗万象的字段表，再让所有详情页都被迫继承。

### 内容结构

内容结构决定详情页由哪些模块组成。

例如产品详情页可以包含：

- 顶部产品摘要
- 主图 / 细节图
- 产品简介
- 参数表格
- 应用场景
- 下载资料
- 相关产品
- 联系按钮

模板中保存的是模块列表和模块顺序，不是某一个产品的具体内容。

推荐的模板编辑方式：

```text
创建模板
  输入模板名称
  生成空模板或最小模板

编辑模板
  从组件库添加组件
  调整组件顺序
  配置组件字段绑定
  配置组件显示规则
  配置组件受控样式
  预览前台详情页
```

也就是说：

```text
需要表格 -> 添加表格组件
需要图片 -> 添加图片 / 图集组件
需要链接 -> 添加链接 / 按钮组件
需要正文 -> 添加文本组件
```

不建议把所有能力都塞进一个 `item_data` 大组件里。`item_data` 可以作为当前阶段的兼容实现和兜底模块，但产品形态上应该逐步拆成更清晰的详情组件。

### 字段绑定

字段绑定决定模块从数据项中读取哪些字段。

当前项目的 `data-*` block 已经支持这类绑定：

```html
<h1 data-name="title" data-type="text" data-fallback="name"></h1>
<img data-name="cover" data-fallback="image,photo,logo" data-type="image">
<div data-name="tags" data-type="list"></div>
```

详情模板应尽量复用这种声明式能力。

常见字段：

```text
title
name
slug
cover
image
photo
logo
summary
excerpt
description
body
content
category
tags
price
date
detail_images
specs
link_url
```

### 显示规则

显示规则决定字段如何被展示。

例如：

- 是否需要细节图
- 细节图最多显示几张
- 图集是否滚动
- 是否自动滚动
- 自动滚动间隔几秒
- 是否显示左右箭头
- 是否显示圆点
- 表格需要几行几列
- 表格是否显示表头
- 表格空单元格是否隐藏
- 链接是否显示
- 没有链接时是否隐藏整个链接模块
- 图片为空时显示占位图还是隐藏模块

这些配置应该用开关、数字输入、下拉选项、颜色选择器等受控表单实现。

### 样式配置

样式配置决定模板允许用户调整的少量视觉参数。

例如：

- 普通文字颜色
- 链接字体颜色
- 标题颜色
- 按钮颜色
- 表格边框颜色
- 表格表头背景色
- 图片圆角
- 模块间距
- 内容宽度
- 对齐方式

样式配置必须受控。用户可以选择颜色或选项，但不能直接写 CSS。

模板需要的 CSS / JS 由系统和模板开发者维护。发布时可以按需打包进静态 HTML 或独立静态资源文件，但源数据中不保存用户手写 CSS / JS。

### 自动生成规则

自动生成规则决定哪些字段可以由系统根据已有内容生成。

例如：

- `slug` 从标题生成
- `summary` 从正文前若干字生成
- 分类从当前列表菜单继承
- 标签从标题、分类、参数中建议生成
- SEO 标题由 `{title} - {site_name}` 生成
- SEO 描述优先使用 `summary`
- SEO 图片优先使用 `cover`
- 相关产品按分类 / 标签推荐

自动生成出来的内容应该允许用户手动覆盖。

## 产品详情模板示例

以产品“LED 灯条”为例。

产品数据项保存具体内容：

```yaml
title: LED 灯条
slug: led-strip
summary: 柔性低压灯带，适合展柜、家装和商业照明
cover: /assets/uploads/led-strip-cover.webp
detail_images:
  - url: /assets/uploads/led-strip-detail-1.webp
  - url: /assets/uploads/led-strip-detail-2.webp
specs:
  - name: 功率
    value: 12W/m
  - name: 电压
    value: DC 24V
category: LED 照明
tags:
  - LED
  - 灯条
link_url: /assets/files/led-strip.pdf
```

详情模板保存组件结构、字段绑定和展示规则：

```yaml
id: product-gallery
name: 图文产品详情
modules:
  - type: detail_media
    variant: default
    data:
      title_field: title
      summary_field: summary
      cover_field: cover
      gallery_field: detail_images
      gallery_max: 6
      gallery_mode: carousel
      show_arrows: true
      show_dots: true
      auto_scroll: true
      scroll_interval_seconds: 3

  - type: detail_text
    variant: default
    data:
      title: 产品简介
      content_field: description
      fallback_field: summary
      empty_behavior: hide_module

  - type: detail_specs
    variant: table
    data:
      source_field: specs
      columns: 2
      max_rows: 8
      show_header: false
      hide_empty_rows: true
      text_color: "#333333"
      border_color: "#e5e7eb"

  - type: detail_link
    variant: button
    data:
      label: 下载资料
      url_field: link_url
      hide_when_empty: true
      link_color: "#0f66d0"

seo:
  title: "{title} - {site_name}"
  description: "{summary}"
  image: "cover"
```

最终渲染时：

```text
模板负责怎么展示
数据项负责展示什么
```

第一阶段如果还没有 `detail_media`、`detail_specs`、`detail_link` 这些独立组件，可以临时用 `item_data` 承载同样的规则，但文档和后台交互应按“组件化详情模板”来设计。这样后续拆分真实前台组件时，数据结构和用户认知都不需要推倒重来。

## 前台预览和渲染原则

详情模板必须同时考虑后台编辑和前台渲染。后台能配置，不代表前台一定能稳定显示；所以模板能力必须以“可预览、可静态生成、可降级”为边界。

### 预览必须使用真实渲染链路

后台预览不应该用一套临时 HTML 拼接逻辑。预览应该尽量复用发布时的渲染链路：

```text
数据项
  -> 解析有效详情模板
  -> 解析组件列表
  -> 合并字段绑定和显示规则
  -> 调用同一套 block_renderer / Jinja 模块
  -> 输出预览页面
```

这样用户在后台看到的效果，才会接近发布后的静态页面。

预览至少需要支持三种入口：

- 数据项预览：看某一条产品 / 案例套用当前模板后的真实效果
- 模板预览：用一条示例数据或当前选中的数据预览模板效果
- 发布前预览：使用构建后的页面路径检查最终 HTML

模板编辑页里的“预览”必须带上当前站点、语言、数据集、模板 ID 和数据项 ID。不要只预览组件配置本身，因为详情模板最终依赖数据项字段。

### 渲染结果必须是静态页面友好的

当前项目发布结果是静态 HTML，所以详情组件不能依赖后台接口才能显示核心内容。

允许：

- 构建时把数据渲染进 HTML
- 构建时按组件需要输出 CSS / JS
- 轮播、折叠、图片切换这类前端交互使用静态 JS
- 没有 JS 时仍然能看到主要内容

不允许：

- 前台详情页打开后再请求后台接口获取核心产品数据
- 依赖登录态才能渲染详情内容
- 预览能看、静态发布后不能看的组件
- 组件输出用户手写的任意 HTML / CSS / JS

### 组件必须有前台渲染契约

每一种详情组件都要定义清楚它的前台契约：

```text
组件类型
  需要哪些字段
  字段为空怎么处理
  输出什么 HTML 结构
  需要哪些 CSS class
  是否需要 JS
  JS 失败时如何降级
  移动端如何显示
```

例如图集组件：

```text
detail_media
  cover_field: cover
  gallery_field: detail_images
  gallery_mode: carousel
  empty_behavior: hide_gallery
  no_js_behavior: show_static_image_list
```

例如规格表组件：

```text
detail_specs
  source_field: specs
  columns: 2
  hide_empty_rows: true
  empty_behavior: hide_module
  mobile_behavior: one_column
```

没有前台渲染契约的配置，不应该出现在模板编辑器里。否则用户能配置出来，但页面无法可靠展示。

### 空值和异常数据不能破版

详情模板要默认防御这些情况：

- 图片缺失
- 图集数量少于模板配置
- 表格行数不足
- 链接为空
- 分类或标签为空
- 富文本为空
- 字段类型不符合预期，例如 `specs` 不是数组
- 图片比例不一致
- 标题过长

处理原则：

- 可选内容为空时隐藏对应组件或对应行
- 必填内容为空时在后台编辑页提示补充
- 图片比例不一致时由前台样式裁切或 contain，不让布局跳动
- 长标题和长链接必须换行或截断，不允许撑破容器
- 表格在移动端必须变成可读布局，而不是横向挤压到不可读

### 预览检查要覆盖桌面和移动端

详情模板不是只看后台表单保存成功，还要看前台页面是否真的好用。

开发完成后至少检查：

- 桌面端详情页是否完整
- 手机端详情页是否不重叠、不横向溢出
- 轮播箭头、圆点、自动滚动是否符合配置
- 图集少图、无图时是否正常
- 表格多行、空行、长文本时是否正常
- 链接为空时按钮是否隐藏
- 切换模板后预览是否变化
- 发布生成的静态 HTML 是否和后台预览一致

这部分应作为详情模板开发的验收标准，而不是后期再补。

## 后台入口

后台菜单配置里，如果某个菜单类型是“列表”，这个菜单项旁边显示“详情模板”管理入口。

建议入口文案：

- “详情模板”
- 或图标按钮，鼠标悬停提示“管理详情模板”

不建议直接叫“创建详情模板”，因为列表菜单应该自动拥有一个默认详情模板，用户更多是在管理和选择。

## 后台流程

### 新建列表菜单

1. 用户创建一个类型为“列表”的菜单，例如“产品中心”
2. 系统创建或关联数据集 `products`
3. 系统创建列表页配置 `pages/products.yaml`
4. 系统创建一个默认详情模板
5. 用户可以先不理解模板，也能直接添加产品并发布详情页

### 编辑列表页

列表页编辑仍然使用现有页面模块系统。

用户可以配置：

- 列表标题
- 数据来源
- 卡片布局
- 显示字段
- 筛选
- 搜索
- 分页
- 查看全部按钮

这些属于列表页模块配置，不属于详情模板。

### 编辑数据项

用户进入某条数据，例如某个产品。

表单应显示：

- 基础字段：标题、slug、封面图、摘要、分类、标签
- 当前详情模板需要的字段：细节图、参数、正文、链接等
- 详情模板选择器
- 预览按钮
- 高级入口

编辑数据项时应支持新窗口或独立预览视图。预览仍然由模板渲染，不进入源码编辑。

### 原有数据集详情编辑

当前项目的数据集编辑页已经支持给单条数据编辑 `modules`。这个能力不要删除，应该重新定义为“高级自定义此条详情页”。

调整后的数据项编辑页建议分成两种模式：

```text
普通模式
  编辑数据字段
  选择详情模板
  预览详情页

高级模式
  自定义此条详情页
  编辑这条数据自己的 modules
```

普通用户默认看到普通模式。只有用户点击“高级”或“自定义此条详情页”时，才进入当前这种模块编辑器。

这样可以保留现有能力，同时避免每条数据都变成独立页面配置。

原有数据的兼容策略：

- 已经有 `item.modules` 的数据继续保留
- 这些 `item.modules` 仍然优先渲染
- 新建数据默认不要写入 `modules`
- 新建数据默认只写基础字段和 `template_id`
- 只有用户进入高级模式并保存时，才写入 `item.modules`

建议提供一个“恢复使用模板”按钮：

```text
恢复使用默认模板
```

点击后：

```yaml
template_id: default
modules: 删除或移到 modules_backup
```

这样这条数据会重新回到列表级详情模板控制。否则一旦每条数据都有自己的 `modules`，以后修改默认模板时，这些旧数据不会跟着更新。

### 管理详情模板

详情模板管理页需要支持：

- 新建模板
- 复制模板
- 编辑模板
- 设为默认
- 预览模板
- 删除模板

删除模板时需要检查：

- 默认模板不能直接删除，必须先设置另一个默认模板
- 正在被数据项使用的模板删除前需要提示
- 删除后，原来使用该模板的数据项可以回落到默认模板

创建模板时的推荐行为：

- 只要求填写模板名称
- 默认创建空模板或最小模板
- 创建后进入模板编辑页
- 用户通过“添加组件”把需要的详情组件加入模板
- 每个组件只暴露它自己需要的字段绑定、显示规则和样式配置
- 保存后立即可以选择一条数据做前台预览

默认模板可以包含一个最小 `item_data` 兜底组件，保证新建列表菜单后不配置也能生成详情页。但用户主动创建的新模板，更适合从空模板开始，避免误以为所有详情页都必须包含图片、表格、链接等所有内容。

## 特殊数据项

少数数据项可能需要和同类内容略有不同，例如某个重点产品需要更多图片、某个案例需要额外下载资料。

这种情况可以提供“高级”入口，但高级入口仍然是受控的：

- 可以切换详情模板
- 可以追加系统已有模块
- 可以覆盖某些字段值
- 可以覆盖少量显示规则
- 可以覆盖少量样式配置

不允许在高级入口中直接编辑 HTML / CSS / JS。

当前项目已经把 `item.modules` 保存到单条数据项里。后续可以把它定义为高级覆盖能力，而不是默认编辑路径。

高级覆盖的推荐存储方式仍然沿用当前结构：

```yaml
modules:
  - type: item_data
    variant: default
    data: {}
```

如果后续需要保留恢复能力，可以在删除覆盖前备份：

```yaml
modules_backup:
  - type: item_data
    variant: default
    data: {}
```

第一阶段可以不做复杂备份，只做“删除覆盖，恢复模板控制”。但操作前需要提示用户。

## 模板反推字段需求

详情模板会决定数据项编辑表单需要显示哪些字段。

例如某个详情模板启用了：

- 细节图
- 参数表
- 下载链接
- 自动标签

那么数据项编辑表单里就应该出现：

- `detail_images`
- `specs`
- `link_url`
- `tags`

规则：

- 模板启用某个模块后，数据项编辑表单显示对应字段
- 模板关闭某个模块后，数据项编辑表单可以隐藏不再需要的字段
- 已有数据不要删除，只是隐藏或标记为未使用
- 多个模板同时存在时，数据项表单显示当前模板需要的字段
- 数据项切换模板时，提示哪些字段会新增、哪些字段暂时不显示

这个能力很重要，因为老板用户不应该看到一大堆永远用不到的字段。

## 空值处理

详情模板必须定义空值处理，否则静态页面容易出现破碎区域。

常见规则：

- 必填字段为空：数据项编辑页提示用户补充
- 可选字段为空：隐藏对应模块或隐藏对应行
- 图片为空：隐藏图片区域或显示默认占位图
- 链接为空：隐藏链接按钮
- 表格某一行为空：隐藏该行
- 图集数量不足：按已有图片显示，不补空位
- 自动生成失败：保留为空，并允许用户手动填写

每个模块应该有默认空值策略，避免用户每次都要理解这些细节。

## 分类和标签

分类和标签建议分开处理。

分类更像结构信息，通常来自：

- 当前列表菜单
- 数据集字段
- 用户手动选择

标签更像辅助信息，可以自动生成：

- 从标题提取
- 从分类继承
- 从参数表关键词提取
- 从用户手动填写的标签合并

建议规则：

- 分类可以自动继承，但允许手动覆盖
- 标签可以自动生成，但允许手动增删
- 自动标签不应该每次保存都强行覆盖用户修改
- 可以记录哪些标签是自动生成，哪些是用户手动添加

## SEO 规则

详情模板应该负责默认 SEO 规则。

例如：

```text
SEO 标题：{title} - {site_name}
SEO 描述：优先使用 summary，没有 summary 时从 body/content 自动截取
SEO 图片：优先使用 cover，没有 cover 时使用第一张 detail_images
```

SEO 规则应该允许数据项手动覆盖。

## 与现有模块系统的关系

详情模板应该复用现有模块系统。

普通页面模块：

```text
字段值 = 直接内容
```

详情模板模块：

```text
字段值 = 数据字段绑定 + 显示规则
```

当前项目的 `item_data` 已经接近这个方向。构建时 `builder.py` 会把当前数据项合并到 `item_data` 模块中，再交给 `block_renderer` 渲染。

后续需要把 `item_data` 做成更明确的“详情模板基础模块”，而不是只依赖隐藏约定。

## 实施路径

### Phase 1：最小闭环

目标：不大改架构，先把现有能力产品化。

- 在 `pages/<dataset>.yaml` 增加 `detail_templates`
- 新建列表菜单时自动生成默认详情模板
- 主动新建详情模板时默认创建空模板或最小模板，不自动塞入所有字段
- 模板编辑页以“添加组件”为核心交互，需要什么组件就加什么组件
- 数据项增加 `template_id`
- 详情页渲染时按“item.modules -> template_id -> 默认模板 -> item_data”解析
- 后台数据项编辑页增加模板选择器
- 保留现有数据项 `modules` 编辑能力，但放到高级入口
- 新建数据默认不生成 `modules`
- 增加“恢复使用模板”操作，允许删除单条数据的 `modules` 覆盖
- 模板管理页先支持复制、设默认、删除
- 预览使用真实详情页渲染链路，而不是后台单独拼一份临时 HTML
- 继续使用现有 `item_data` 模块和 `_generic_detail.html`

### Phase 2：字段需求和表单优化

目标：让老板只看到当前模板需要填的字段。

- 从详情模板组件中收集字段需求
- 数据项编辑表单按当前模板显示字段
- 切换模板时提示字段变化
- 已有字段隐藏但不删除
- 支持基础自动生成：slug、摘要、SEO 标题、SEO 描述、标签建议
- 模板预览支持选择数据项，能看到字段缺失、空值隐藏和组件降级效果

### Phase 3：模板能力增强

目标：让详情模板真正覆盖常见详情页需求。

- 为详情组件补充 meta schema，第一阶段可由 `item_data` 兼容承载
- 拆出更明确的详情组件，例如 `detail_media`、`detail_text`、`detail_specs`、`detail_link`、`detail_related`
- 支持细节图数量、箭头、圆点、自动滚动、滚动间隔
- 支持参数表行列、空行隐藏
- 支持链接按钮和颜色配置
- 支持相关产品模块
- 支持更多详情页 variant
- 每个详情组件都定义前台渲染契约、移动端行为和无 JS 降级

### Phase 4：收敛单条 modules

目标：减少数据项重复配置。

- 把大多数 `item.modules` 迁移成列表级详情模板
- 只把少数特殊数据项保留为高级覆盖
- 提供“从此条生成模板”功能
- 提供“将此模板应用到未覆盖数据项”功能

## 不做

为了符合产品定位，详情模板需要限制范围：

- 用户不能编辑 HTML
- 用户不能编辑 CSS
- 用户不能编辑 JS
- 不引入 Grapes.js 这类整页可视化编辑器
- 不做自由拖拽布局系统
- 不做全站通用动态模板语言
- 不把用户手写的 HTML / CSS / JS 保存进单条数据项

用户可以做的是：

- 选择模板
- 选择模块
- 调整模块顺序
- 选择模块 variant
- 绑定字段
- 配置显示规则
- 配置系统允许的样式项
- 配置自动生成规则
- 在高级入口做受控覆盖
- 预览效果

发布后的 HTML 可以包含模板生成的 HTML / CSS / JS，但这些是构建结果，不是用户编辑的源数据。

## 判断标准

这个功能做对的样子：

- 新建一个列表菜单后，不配置任何东西也能生成详情页
- 多条产品可以共用同一个详情模板
- 修改默认详情模板后，未覆盖的数据项自动更新展示
- 特殊产品可以单独覆盖，但不会污染其他产品
- 原来已经用 `item.modules` 自定义过的详情页继续可用
- 新建数据默认跟随详情模板，不再自动生成独立 `modules`
- 用户可以把单条数据恢复为使用模板
- 数据项编辑页只出现当前模板需要的字段
- 静态导出后，详情页不依赖后端服务
- 用户始终在填表，不接触源码
