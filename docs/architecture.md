# 架构设计

## 一、参与角色

系统服务三类人：

| 角色                | 是谁                       | 做什么                                |
| ------------------- | -------------------------- | ------------------------------------- |
| **开发者 / 设计师** | 平台方（你 + AI + 设计师） | 用代码 + AI 制作模板，提交到 git      |
| **店主**            | 小企业老板                 | 选模板、填表、发布、看数据            |
| **访客**            | 店主网站的浏览者           | 浏览静态 HTML（看不到我们平台的存在） |

关键洞察：**店主一辈子不接触代码，模板始终是代码（git 管理）。**

## 二、整体数据流

```text
[开发者 + AI]   设计模板 → 写 HTML / Jinja2 / CSS → git push
                                ↓
                          模板加入模板库
                                ↓
[店主]    选模板 → 表单填数据 → 上传图片 → 点击「发布」
                                ↓
[系统]    数据 + 模板 → 渲染 → 字体子集化 → 静态文件
                                ↓
                            上传到 CDN
                                ↓
[访客]    浏览器访问 → CDN 直接返回 HTML（< 1 秒）
```

## 三、模块概览

```text
                  模板库（site_templates/，git 管理的文件夹）
                          │
                          ▼
┌────────────────────┐    ┌────────────────────┐    ┌────────────────────┐
│   店主后台          │───▶│  Flask 后端 API     │───▶│   静态生成器        │
│  (表单 + 数据管理)  │    │  (路由 / 业务逻辑)   │    │  (渲染 + 优化)      │
└────────────────────┘    └─────────┬──────────┘    └─────────┬──────────┘
                                    │                          │
                                    ▼                          ▼
                              数据库（用户数据）             CDN（静态文件）
                                                              │
                                                              ▼
                                                          访客的浏览器
```

注意：**没有「设计师后台」模块**。模板由开发者写代码做，工具就是 IDE + git + AI。

## 四、数据分两层（重要架构决策）

整个系统的数据分两层存放：

```text
                ┌───────────────────────────┐
                │  数据库（平台级）           │
                │  - User（账号）             │
                │  - Site（站点元信息）       │
                │  - PublishVersion（发布历史）│
                │  - Billing（计费）          │
                └───────────────────────────┘
                            │
                            │  Site.folder_path → 指向
                            ▼
                ┌───────────────────────────┐
                │  文件系统（站点级）         │
                │  sites/<site_id>/          │
                │  - settings.yaml           │
                │  - pages/*.yaml            │
                │  - data/*.yaml             │
                │  - translations/*.yaml     │
                │  - assets/                 │
                └───────────────────────────┘
```

**店主网站的核心数据存为文件，不存数据库。**

为什么：

- "导出 ZIP" = 复制一个文件夹，不需要序列化逻辑
- 平台关停时把文件夹给店主，整站还能跑
- schema 弹性：模板换字段不用 ALTER TABLE
- AI 友好：可直接读 YAML 调试、修复
- 跟"模板是文件夹"心智模型统一

### 核心数据模型

> 字段细节见 [database.md](database.md)，模板 / 块 / 数据集的概念见 [templates.md](templates.md)。

| 实体           | 存在哪里                              | 说明                                                          |
| -------------- | ------------------------------------- | ------------------------------------------------------------- |
| Template       | `site_templates/<name>/` 文件夹       | 模板（代码 + 资源），git 管理                                 |
| User           | 数据库                                | 店主账号（邮箱魔法链接登录）                                  |
| Site           | 数据库                                | 站点元信息（id、owner、template、folder_path、custom_domain） |
| PublishVersion | 数据库                                | 一次发布的快照（version、cdn_url、timestamp）                 |
| Billing        | 数据库                                | 计费记录                                                      |
| SiteSettings   | `sites/<id>/settings.yaml`            | 站点配置（菜单项、主题变量、开关、启用的语言）                |
| Page 字段值    | `sites/<id>/pages/*.yaml`             | 每个页面的内容                                                |
| Dataset        | `sites/<id>/data/<name>.yaml`         | 数据集（产品 / 案例 / 博客）                                  |
| DataItem       | 同上文件中的一项                      | 数据条目（一个产品 / 一篇案例）                               |
| Translations   | `sites/<id>/translations/<lang>.yaml` | 多语言翻译缓存                                                |
| Glossary       | `sites/<id>/glossary.yaml`            | 翻译词汇表                                                    |
| Asset          | `sites/<id>/assets/` 文件             | 上传的图片 / 文件                                             |

## 五、关键技术决策

### 为什么用 Flask

轻量、Python 生态成熟、Jinja2 直接复用做静态生成。
MVP 阶段不需要重武器。

### 为什么静态生成而不是 SSR

定位上就是「发布完不动」的网站。SSR 意味着永远在运行，违背产品理念。

### 为什么 SQLite 起步

MVP 阶段单机就够。每个店主的数据量很小（几十个产品 + 几十张图）。
当用户上千、并发上来再换 PostgreSQL。

### 为什么站点数据存文件而不是数据库

每个店主网站的核心内容（settings、pages、products 等）存为 YAML 文件，
而不是关系型数据库表。原因：

- **导出 = 复制文件夹**，无需序列化逻辑
- **schema 弹性**：模板字段变化不需要 ALTER TABLE
- **多语言天然嵌套**：YAML 自然支持
- **AI 友好**：直接读、改、调试
- **平台死了，店主拿到文件夹仍能跑**

代价（在小企业站规模下基本不存在）：

- 跨用户运营报表 → 关键统计回写到 SQL 冗余字段
- 单站搜索产品 → 几百条 YAML 全文扫描足够快
- 并发写入 → 单店主单写者 + 文件锁

跟 Hugo / Jekyll / Eleventy 同一思路（纯文件 + 静态生成），
不跟 WordPress / Shopify（数据库 + 运行时渲染）。

### 为什么模板是文件不是数据库

模板少（3-5 套）、变更频率低、需要 review 和版本控制。
git 是已经为这种场景设计的最佳工具：

- diff / blame / branch / PR 全部可用
- 模板代码可以被 AI 直接读和改
- 没有「JSON → HTML」的转换层，渲染就是纯 Jinja2
- 部署模板更新 = git pull + 重启服务

### 为什么不用可视化模板编辑器

3-5 套模板不值得为它建一整套可视化系统（Grapes.js 等）。

2026 年 AI 写 HTML / CSS 已经很好用：设计师给 Figma 截图，AI 出 HTML 骨架，开发者微调。
模板做完就稳定了，不需要持续可视化编辑。

将来真要做"第三方设计师上架卖模板"的开放生态，到时候再加 —— 不应该让 MVP 为这种远期可能性买单。

### 为什么不分前后端

店主端只是表单，复杂度低，Flask + 少量 vanilla JS 足够。
**避免引入 Vue / React 增加新人上手门槛。**

### 为什么图片在录入时就处理

用户一定会传 5MB 手机原图。等到发布时再批量压缩，会让发布变慢；
而上传时压一次，店主感觉是"上传完成"，体验更好。

## 六、目录结构（提议）

```text
mycompany.website/
├── app/                    # Flask 应用
│   ├── core/               # 数据模型、配置
│   ├── auth/               # 邮箱魔法链接登录
│   ├── shop/               # 店主后台（表单、数据管理、发布触发）
│   ├── publish/            # 发布服务（生成器 + CDN + 字体子集化）
│   ├── templates/          # Flask Jinja2 模板（管理界面）
│   └── static/             # 前端资源（管理界面用）
├── site_templates/         # 模板库（git 管理）
│   ├── manufacturing-standard/
│   ├── restaurant-standard/
│   └── service-standard/
├── sites/                  # 店主网站数据（每个店主一个文件夹）
│   └── <site_id>/
│       ├── settings.yaml
│       ├── pages/
│       ├── data/
│       ├── translations/
│       └── assets/
├── fonts/                  # 预装的可商用字体（思源、阿里普惠、OPPO Sans 等）
├── docs/                   # 设计文档
├── output/                 # 生成的静态网站（临时，发布后上传 CDN）
├── CLAUDE.md
├── README.md
└── run.py
```

每个模板的内部结构详见 [templates.md](templates.md)。

## 七、不在 MVP 范围

为了让 MVP 能跑起来，下面这些先不做：

- 多语言（Phase 2，创始人 dogfooding 时上线）
- 异步任务队列 / Celery（一开始同步发布够用）
- 复杂权限系统（一个店主一个站就行）
- 用户上传自定义模板（只能用平台内置）
- 在线模板市场
- 评论 / 用户系统
- 可视化模板编辑器
