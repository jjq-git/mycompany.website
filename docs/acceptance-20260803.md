## 四、上线阻断项

### P0-0 正式发布链路未实现，现有接口会假报“已发布”

专项隔离验收确认：`/publish` 在临时目录完成构建后删除产物，仅把数据库状态和时间改为已发布。它没有执行 OSS/CDN 上传、线上版本切换、公网回读、发布历史或回滚；发布后继续编辑也不会标记“有未发布变更”。

部署前必须按[建站至发布业务链路专项验收](acceptance-site-lifecycle-20260803.md)中的 LIFE-P0/P1 全部整改并复验。修复前必须继续禁用发布入口，不得把接口成功响应当作网站已上线。

### P0-1 当前有效配置关闭私有预览鉴权

验收时有效 `.env` 的 `PREVIEW_REQUIRE_LOGIN=0`。

代码在该值为 0 时允许匿名访问 `preview`、`preview_site`、`preview_or_build`。路由仍接受数字 ID 作为兼容输入，因此存在枚举未发布站点的风险。

正式部署要求：

```env
PREVIEW_REQUIRE_LOGIN=1
```

复验标准：

- 匿名访问三个真实站点预览入口均不得返回站点内容。
- 已登录的其他用户访问非本人站点必须返回 403。
- 本人、被授权协作者和平台管理员按权限正常访问。

### P0-2 当前有效配置关闭导出死链门禁

验收时有效 `.env` 的 `EXPORT_SKIP_LINK_CHECK=1`。

这会使构建已经报告死链时仍允许导出 ZIP，与“不能让店主拿到缺页站点”的产品约束冲突。

正式部署要求：

```env
EXPORT_SKIP_LINK_CHECK=0
```

复验标准：人为制造一条站内死链后，构建报告必须记录，导出和发布必须被阻止；修复后才能成功。

### P0-3 生产环境标识缺失，Session Cookie 未带 `Secure`

验收时 `.env` 未设置 `FLASK_ENV=production`。当前代码只有显式生产环境才设置 `SESSION_COOKIE_SECURE=True`。

已动态复现：

```text
SESSION_COOKIE_SECURE=False
Set-Cookie: ...; HttpOnly; Path=/; SameSite=Lax
```

正式部署要求：

```env
FLASK_ENV=production
FLASK_DEBUG=0
```

复验标准：HTTPS 响应中的 Session Cookie 同时带 `Secure`、`HttpOnly`、`SameSite=Lax`；HTTP 入口只允许跳转 HTTPS。

### P1-1 CSRF 失败处理存在外部重定向

`app/__init__.py` 的 CSRF 错误处理直接执行：

```python
redirect(request.referrer or request.url)
```

已用外站 Referer 动态复现：

```text
POST /login（缺 CSRF）
Referer: https://evil.example/phish
响应: 302 https://evil.example/phish
```

修复要求：Referer 必须经过同源/本站相对路径校验；无法确认时回登录页或当前本站 URL，不得跳转到外部域名。

复验标准：`https://evil.example/...`、`//evil.example/...`、伪协议和异常 Referer 都不能进入 `Location`。

### P1-2 缺少全局安全响应头

登录页实测缺少：

- `Content-Security-Policy`
- `X-Content-Type-Options`
- `X-Frame-Options` 或 CSP `frame-ancestors`
- `Referrer-Policy`
- `Permissions-Policy`
- `Strict-Transport-Security`

修复要求：建立全局 `after_request` 安全头策略。后台当前包含大量内联脚本，CSP 不能直接粗暴设为 `script-src 'self'`，需先采用 nonce/哈希或分阶段收紧。

### P1-3 生产依赖与部署启动方式不完整

当前 `requirements.txt` 未声明 Gunicorn/Waitress 和 PostgreSQL 驱动，但代码与文档声称生产使用 WSGI/PostgreSQL。本机全局环境中已有这些包，掩盖了新机器安装失败风险。

同时，`docs/deployment.md` 仍把 `python run.py` 写成正式启动命令。该命令只能用于本地/初始化验证，不得作为公网生产服务。

修复要求：

1. 明确 Linux 或 Windows 的正式 WSGI 方案。
2. 将 WSGI 服务、数据库驱动加入部署依赖。
3. 增加可复现锁定文件或固定兼容版本范围。
4. 用 systemd/Windows 服务管理器托管，配置自动重启和日志轮转。

### P1-4 业务站点资料仍被 Git 跟踪

虽然 `.gitignore` 已包含 `sites/`，但站点 5/6 的旧文件已进入 Git，忽略规则不会自动解除跟踪。

## 五、中优先级问题

### P2-1 模板公开状态与路由白名单不一致

数据库中 Airbnb、Apple、Blank、Claude、Dengtec、Notion 六个模板均为 `is_public=true`，但路由硬编码只允许：

```python
VISIBLE_TEMPLATE_NAMES = ('blank', 'claude', 'dengtec')
```

因此 Airbnb、Apple、Notion 预览返回 404。部署前必须明确：要么下线并设为非公开，要么纳入可见列表并完成预览验收。

### P2-2 首页首屏加载策略不理想

站点 6 首页静态指标：

- HTML：约 69 KB
- 主 CSS：126,274 字节
- 首张 Hero 图：57,698 字节，但设置了 `loading="lazy"`
- 第二张 Hero 自动播放视频：5,266,248 字节

首屏主图懒加载可能推迟 LCP；自动播放视频即使配置 `preload="none"`，浏览器仍可能因 `autoplay` 很快拉取资源。

部署前要求：首张可见 Hero 图取消懒加载并配置高优先级；非激活视频延迟设置 `src`，进入对应轮播页时再加载。

### P2-3 依赖不可完全复现

当前依赖全部使用 `>=` 下限，没有锁文件。不同机器或不同时间安装可能得到不同 Flask、Werkzeug、SQLAlchemy、Pillow 组合。

部署前要求：生成经测试的锁定依赖，并在全新环境中执行一次从零安装和全量复验。

### P2-4 数据库迁移仍是启动时手工迁移

应用启动时执行 `db.create_all()` 和若干手写迁移。SQLite 当前完整性通过，但 PostgreSQL 切换、回滚、并发启动和多实例部署缺少正式迁移历史。

部署前要求：建立 Alembic/Flask-Migrate 迁移基线，至少验证空库初始化、现有库升级、失败回滚和重复执行。

### P2-5 代码集中度过高

- `app/core/routes.py`：约 8008 行
- `app/core/builder.py`：约 2716 行
- `panel_page_edit.html`：约 3778 行
- `panel_data_list.html`：约 2800 行
- `base.html`：约 2725 行

这不直接阻断部署，但会放大安全修复和 UI 改动的回归风险。应在自动化测试恢复后再按认证、媒体、内容、构建、发布等边界拆分。

### P2-6 文档实现状态已过期

`implementation-status.md` 最后更新于 2026-06-03，仍将多语言、ZIP 导出、平台管理员、发布状态等当前已有能力标为未实现。部署前要按代码实际行为重新核对，避免运维和验收使用旧结论。
