# 筛选标签（自动生成 + 手动修改）

列表页（`data_grid` 等）顶部的「标签」筛选栏，是访客按维度筛选产品的入口。
本文说明这些标签**从哪来、怎么生成、怎么被手改覆盖**，以及各数据集当前的处理策略。

## 一句话结论

> 前台筛选栏的按钮 = 把当前列表里**每个条目的 `tags`** 聚合去重后自动生成。
> 条目的 `tags` 可以**由结构化规格自动派生**，也可以**手动填写**；手改一旦发生，之后不再被自动值覆盖。

## 数据链路（谁生成、谁覆盖、谁展示）

| 环节 | 位置 | 职责 |
|---|---|---|
| 生成规则 | [app/core/tagging.py](../app/core/tagging.py) `generated_technical_tags()` | 从结构化规格字段派生标签（尺寸分桶、电气取值等） |
| 保存时写入 | [app/core/routes.py](../app/core/routes.py) `_apply_detail_template_autofill()` | 保存产品时按规格刷新 `tags`；检测手改并锁定 |
| 渲染时兜底 | [app/core/builder.py](../app/core/builder.py) → `with_generated_tags()` | 构建/预览时对「归自动管理或无标签」的条目补算，**尊重手改** |
| 前台聚合 | `site_templates/<模板>/templates/_base.html` `initFilterableGrids()` | 扫描每张卡片 `.dg-card-tag`，聚合去重生成筛选按钮 |

关键点：**前台筛选栏不是手工配置的按钮**，改变某个产品的 `tags` 就会改变筛选栏。

## 标签格式：`前缀-值`

所有自动标签统一形如 `width-1020`、`color-3000K`、`voltage-12v`。前缀代表**筛选维度**，
由规格字段的**名称**匹配决定（`_TAG_PREFIX_RULES`，别名用 substring + 转小写匹配，
同时覆盖简体 / 繁体 / 英文，避免多语言站点某个语言维度缺失）。

当前内置维度：

| 前缀 | 含义 | 匹配的字段名（部分别名） | 取值方式 |
|---|---|---|---|
| `chip` | 灯珠/芯片型号 | 灯珠封装、封装型号、chip、package | 原值 |
| `color` | 色温/颜色 | 色温、颜色、color、colour | `3000K` 归一为 `3000K`；其余转小写 |
| `pitch` | 灯珠密度 | 灯珠数、密度、pitch、led density | 取数字 |
| `voltage` | 电压 | 输入电压、电压、voltage | 取 `12v` 形式 |
| `lswidth` | 灯板宽度 | 灯板宽度、stripwidth、led board width | **区间分桶** |
| `width` | 宽度 | 宽度、板宽、width | **区间分桶** |
| `height` | 高度 | 高度、height | **区间分桶** |

> ⚠ **顺序敏感**：`lswidth`（灯板宽度）必须排在 `width` 前面。它的字段名含「宽度 / width」，
> 若 `width` 规则在前会先命中，导致灯板宽度被错分到 `width` 维度。新增维度时注意这类包含关系。

### 尺寸类为什么要「区间分桶」

宽度 / 高度 / 灯板宽度若按**精确值**生成（`width-15.8`、`width-12.4`……），
几乎每个产品一个值，筛选栏会出现几十个按钮，失去筛选意义。因此归入固定区间桶：

| 数值范围 | 桶 |
|---|---|
| < 10 | `-10` |
| 10 ~ 20 | `-1020` |
| 20 ~ 30 | `-2030` |
| ≥ 30 | `-30` |

例：宽度 15.8 → `width-1020`，宽度 39 → `width-30`。桶边界与最初批量导入脚本口径一致。
（分桶前缀在 `tagging.py` 的 `_BUCKET_PREFIXES` 定义。）

## 手改优先：`tags_auto` 标记

条目上有一个布尔字段 `tags_auto`，决定标签归谁管理：

| `tags_auto` | 含义 | 保存 / 渲染时行为 |
|---|---|---|
| `true` | 归自动管理 | 按规格重算并刷新 `tags` |
| `false` | 用户已手动接管 | **保留手填 `tags`，永不覆盖** |
| 缺失 | 未知 | 已有非空 `tags` → 视为别处生成/手填，保留；无 `tags` → 自动补算 |

**手改检测**（发生在保存时，`_apply_detail_template_autofill`）：
提交的 `tags` 与本次自动值不一致 → 判定用户手动改过 → 置 `tags_auto=false` 永久锁定。
表单默认回填的就是上次自动值，用户没动则两者相等，不会误锁。

后台编辑页的「标签」输入框**可编辑**（预填自动值），直接修改保存即触发上述锁定，
面板会显示「（已手动修改）」提示。

## 各数据集当前处理策略

自动生成规则是为**尺寸 / 电气类维度**（铝型材、灯条）设计的，靠「字段名匹配」派生。
对维度性质不同的品类会误判，因此并非所有数据集都走自动重算：

| 数据集 | 标签来源 | 是否自动重算 | 原因 |
|---|---|---|---|
| aluminum-profile（铝型材） | 结构化规格 → 尺寸桶 | ✅ 已重算 | 宽/高/灯板宽能被识别，区间桶干净 |
| led-strip（灯条） | 脚本生成多维（chip/color/pitch/voltage/width） | ❌ 保持现状 | 现有多维标签质量高于自动逻辑；重算会冲掉 color/pitch 且三语言不一致 |
| holograms（全息投影） | 脚本生成业务维（bt/直径/遥控/同步/无线） | ❌ 保持现状 | 业务维度无法用「字段名匹配 + 分桶」表达，自动逻辑会误判成 pitch |
| powerptrack / projects / blog | 手填或脚本业务标签 | ❌ 保持现状 | 手填业务词，自动逻辑生成不了 |

> 判断新数据集是否适合自动标签：它的筛选维度是不是「尺寸 / 电气」这类能从规格字段名匹配、
> 数值能分桶的？如果是布尔枚举（有/无）或业务分类词，当前自动逻辑不适用，应保持手填。

## 局限与后续方向

当前机制的本质是**内置别名表「猜字段名」**：加一个新品类维度，往往要回到 `tagging.py`
补别名 / 加规则，不是真正通用。更彻底的通用方案（留待后续评估）是：
让店主在规格参数里**勾选「哪些字段作为筛选维度」**，系统按勾选生成标签（数值自动分桶、
枚举直接取值），任何新品类都不必改代码。此方案改动较大（规格块字段 + 后台 UI + 生成逻辑 + 迁移），
未在当前范围内实施。
