## 店主后台（内容管理界面）

### 设计原则
- 不显示「块」「模板」「组件」这些技术词
- 主界面是数据列表，不是可视化编辑器
- 任何编辑都是表单，不是拖拽
- 店主**永远不接触代码、不打开任何"设计"工具**

### 菜单与页面的关系（关键）
**除了首页 index 是固定页面外，其余菜单项自动生成对应页面。** 菜单配置是页面渲染的驱动源。

#### 核心规则

| 页面 | 规则 |
| --- | --- |
| 首页（index） | **固定页面**，始终渲染。使用 `index.html` 模板 + `pages/home.yaml` 数据 |
| 其他菜单 | **由菜单驱动**。店主在头部配置中创建新菜单 → 自动成为可渲染的页面 |

#### 自动生成流程

```text
店主在后台新建菜单项 "服务 (service)"，type = "list"，target = "services"
        ↓
系统在 settings.yaml 写入：
    menu:
      - label: "服务"
        type: list
        target: services
        ↓
渲染时读取 settings.yaml 的 menu 列表：
    1. 首页 index → 固定渲染，用 index.html
    2. 遍历 menu 中每个 type 非 home 的项 → 动态渲染：
        ├── target = "services" → 在模板目录查找 services.html
        │   ├── 找到 → 渲染 services/index.html
        │   │        页面数据来源：data/services.yaml（数据集列表页）
        │   │        详情页：若 data/services.yaml 每条有 slug → 生成 /services/<slug>/index.html
        │   │        模块库：同首页，店主可为 services 页面选择/排序模块
        │   └── 未找到 → 警告 "模板缺少 services.html"，该页面仍注册但渲染时跳过
        └── 如果是 link 类型 → 不生成页面，仅作为导航链接
```

#### 菜单类型与页面生成规则

| type | 是否生成页面 | 模板文件 | 数据来源 | URL |
| --- | --- | --- | --- | --- |
| `home` | 固定生成（index） | `index.html` | `pages/home.yaml` | `/` |
| `list` | 自动生成 | `<target>.html` | `data/<target>.yaml`（数据集） | `/<target>/` |
| `page` | 自动生成 | `<target>.html` | `pages/<target>.yaml`（单页） | `/<target>/` |
| `link` | 不生成页面 | — | — | 外链或自定义 URL |

#### 数据集自动映射为页面

当菜单 type 为 `list` 且 `target` 指向一个数据集名时：

| target | 模板文件 | 数据文件 | 生成结果 |
| --- | --- | --- | --- |
| `products` | `products.html` | `data/products.yaml` | 产品列表页 + 每个产品的详情页 |
| `services` | `services.html` | `data/services.yaml` | 服务列表页 + 每个服务的详情页 |
| `cases` | `cases.html` | `data/cases.yaml` | 案例列表页 + 每个案例的详情页 |
| `posts` | `blog.html`（或 `posts.html`） | `data/posts.yaml` | 博客列表页 + 每篇文章的详情页 |

只要模板中存在对应的 `.html` 文件且数据集有数据，页面就能完整渲染。

#### 单页自动映射

当菜单 type 为 `page` 时：

| target | 模板文件 | 数据文件 | 生成结果 |
| --- | --- | --- | --- |
| `about` | `about.html` | `pages/about.yaml` | 关于我们页 |
| `contact` | `contact.html` | `pages/contact.yaml` | 联系我们页 |
| `team` | `team.html` | `pages/team.yaml` | 团队介绍页 |

#### 菜单删除与关联检查

**除了首页 index 不可删除外，所有菜单项都可以删除。** 但删除前系统会检查关联关系并给出提示：

```text
店主点击菜单项"服务"的 [✕ 删除]
        ↓
系统执行关联检查：
  ├── 检查是否有页面数据 (pages/services.yaml)
  │   → 有 → 提示 "该菜单关联了页面数据，删除后 /services 将无法访问"
  ├── 检查是否有数据集 (data/services.yaml)
  │   → 有 → 提示 "该菜单关联了数据集（含 12 条服务记录），删除后数据保留但不再显示"
  ├── 检查是否有详情页引用 (其他数据集条目 link 到 /services/xxx)
  │   → 有 → 提示 "有 3 个产品引用了 /services 下的链接，这些链接将失效"
  ├── 检查是否有子菜单
  │   → 有 → 提示 "该菜单下有 2 个子菜单项，将一并被删除"
  └── 是否有 SEO 索引 → 提示 "搜索引擎将无法访问 /services"
        ↓
弹出确认对话框：
    ┌─────────────────────────────────────────────┐
    │  ⚠ 确认删除菜单"服务"？                       │
    │                                             │
    │  影响范围：                                   │
    │  • 页面 /services/ 将被移除                   │
    │  • 数据集"services"（12 条）保留但不再显示    │
    │  • 3 个产品中的链接将失效                     │
    │                                             │
    │  [取消]  [确认删除]                          │
    └─────────────────────────────────────────────┘
```

删除后：
- `settings.yaml` 的 `menu` 列表中移除该项
- 对应的页面 YAML 数据**保留**（soft-removed，30 天内可恢复：在 settings.yaml 中标记 deleted_at 时间戳）
- 对应的数据集**保留**（不删除数据，店主可能以后重新创建菜单）
- 删除操作记录到 `audit_log`

#### 与传统 CMS 的对比

| 维度 | 传统 CMS（WordPress 等） | 本项目 |
| --- | --- | --- |
| 创建页面的方式 | 后台点"新建页面" | **创建菜单即创建页面** |
| 页面模板 | 从主题的页面模板列表中选择 | 由模板开发者预提供，按 `target` 自动匹配 |
| 模块/内容 | Gutenberg / 拖拽编辑器 | 模块库选择 + 排序 + 填表 |
| 数据存储 | MySQL 数据库 `wp_posts` 表 | `sites/<id>/pages/<target>.yaml` 或 `data/<target>.yaml` |

**关键洞察**：店主不需要理解"页面"概念。他们只做两件事——**创建菜单**（导航结构）和**填内容**（模块数据）。系统根据菜单自动搞定页面生成。

店主在后台填的所有内容，落到文件系统中的这个结构（完整树见 [目录结构.md](../目录结构.md)）：

```text
sites/<site_id>/                    # 一个店主网站的全部数据，每站一个文件夹
├── settings.yaml                   # 站点配置（菜单树、Header 变体、启用的语言、主题变量）
├── glossary.yaml                   # 翻译词汇表（店主指定的固定翻译）
├── pages/                          # 单页内容（菜单 type=page，如 about/contact）
│   ├── home.yaml                   # 首页（固定页面）的模块配置
│   ├── about.yaml
│   └── contact.yaml
├── data/                           # 数据集（菜单 type=list，循环渲染）
│   ├── products.yaml               # 产品列表
│   ├── posts.yaml                  # 博客文章
│   └── cases.yaml                  # 案例
├── translations/                   # AI 翻译缓存（按语言分文件）
│   ├── en.yaml                      # 存 hash→译文 的查找表，不是成品英文站；成品发布时拼进 output/en/
│   └── zh-Hant.yaml
└── assets/                         # 上传的资源文件
    └── images/                     # 店主上传的图片（上传时已转 WebP）
```

后台的「创建菜单」写入 `settings.yaml` 的 `menu`，「填内容」写入对应的 `pages/*.yaml` 或 `data/*.yaml`——这就是后台操作与文件的全部对应关系。

### 后台布局
管理后台整体分左中右三块：

- **左侧**：配置菜单，包括网站基础配置（网站宽度、主题颜色、是否多语言）、网站头部、网站底部、其他菜单（来源网站头部配置了哪些网站菜单，选择这些菜单做相应的配置，而且这些菜单除了首页 index，其他都可以配下级菜单）
- **中间**：预览
- **右侧**：选择左侧菜单的属性（包括预览里面所需的模块，这些模块事先设计好，而且模块都是通用的）

### 登录方式
**邮箱魔法链接，不要密码。**

- 输入邮箱
- 收到一封带链接的邮件
- 点击链接即登录

低频用户记不住密码。免去"忘记密码"流程。

### 帮助系统：随手可得 + 聪明触发
- 界面右上角常驻 **`?` 图标**
- 首次进入某界面自动展示一次指引
- 距上次登录 > 60 天有温和回归提示
- 用了新功能有红点提示

### 四个自定义口子
不开放完整的"开发者模式"，但提供四个明确的口子：

1. **自定义 HTML 块** —— 在任何页面加一段自己的代码
2. **全站 head 注入** —— 加百度统计、客服系统等脚本
3. **全站自定义 CSS** —— 微调样式
4. **整站导出 ZIP** —— 想完全控制？拿走自己改

这四个口子能消化 95% 的"我想动一下"需求，又不会污染核心产品。
